How I work

Evidence first, then the demo.

More about me

I'm most useful when a problem is still fuzzy: the data is uneven, the evaluation is unclear, and the product expectations are ambitious. My instinct is to make the uncertainty visible, then reduce it one measured step at a time.

Start with the failure mode

Before adding a model or a tool, I want to know what breaks in practice. That usually changes the design more than a new framework does.

Measure the thing you claim

Retrieval, faithfulness, latency, and class-level recall all tell different stories. I try to report the one that matches the claim, including when it is inconvenient.

Leave the system legible

Clear interfaces, observable failures, and documentation matter. A system that cannot be debugged is not finished, even if the demo looks good.
