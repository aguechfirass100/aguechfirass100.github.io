About

A practical engineer for uncertain systems.

I’m Firas Aguech, an AI engineer in Sfax, Tunisia. I like the part of the work where a model stops being a demo and has to answer a real question, with evidence, limits, and a human still in the loop.

I work across retrieval, evaluation, agents, and the application boundaries that make an AI feature usable. The through-line is not a particular model. It’s the habit of checking what the system actually does.

I started in software engineering, then moved toward machine learning and data science. At ESPRIT, I worked on a transformer-based network intrusion detector where the aggregate score looked strong but one class still failed a third of the time. That experience shaped how I read metrics: the average is a starting point, not the conclusion.

At MediaCockpit, I work on Cockpit AI’s assistant layer inside an existing enterprise platform. I’ve built tool contracts, cross-collection retrieval, review-before-save flows, and an evaluation loop. The reranker improved ranking quality and cost 26 seconds of CPU latency; both facts belong in the story. I’ve also migrated the assistant from MC14 to MC15 and kept those results separate.

Before that, I contributed to a shipped mobile app at Smartegy and built teachers.tn, an Arabic-first education platform that is still live. Those projects keep me honest about the difference between “the model works” and “the product works.”

How I work

A few principles I keep coming back to.

Measure the thing you’re claiming.

If a change is supposed to improve retrieval, name the set, the metric, and the failure mode. A benchmark without a boundary is marketing.

Keep the human in the loop.

For consequential actions, the assistant should propose and the user should approve. The normal platform save path is a feature, not a limitation.

Make failure legible.

A missing document, a failed tool call, and a low-confidence answer are different failures. Collapsing them into one “something went wrong” message helps no one.

Write down the limits.

Development set, read-only access, no A/B test. Saying what the evidence does not cover is part of the engineering.
