Cockpit AI

Context

MediaCockpit is an enterprise product information management and digital asset management platform. Product data lives across nodes, attributes, assets, PDFs, and background workflows. The platform already owns the domain services; the difficulty is connecting the right operation and the right evidence to a user’s actual task.

Cockpit AI adds a conversational coordination layer inside the portal. A user can ask for a product, compare records, inspect a document, review a proposed attribute, or ask what is happening on the current page. The assistant should not guess its way through those tasks. It should select a bounded operation, return evidence, and keep the human in control of changes.

My role and scope

I worked on the assistant layer inside an existing Java platform — not as a greenfield replacement. My contribution covered assistant-facing context, typed tool contracts, orchestration, product and document retrieval, interface integration, the MC15 migration, and the evaluation loop.

Existing platform services remained responsible for product data, permissions, editing, and workflow behavior. That division matters: the assistant does not receive arbitrary database access. It calls application operations with explicit contracts and passes the result back into the conversation.

Scope note

The measured evaluation describes the MC14 implementation. MC15 migration work is documented separately. I do not transfer MC14 metrics to MC15 as proof of feature parity.

The design problem

A product question is not one retrieval problem. An external key should resolve as exact identity data. A descriptive request may need semantic retrieval. A PDF question needs page-labelled document evidence. A request to edit an attribute should stage a proposal, not silently write to the database.

The assistant therefore separates three things: context (who and where the user is), capabilities (what operations are available), and evidence (what the operation actually returned). The model can choose among tools, but the application enforces execution boundaries and save semantics.

  • Context is explicit. The portal supplies the active page, locale, user, document workspace, and session history.
  • Tools are typed operations. Lookup, structured filtering, semantic search, document retrieval, navigation, and reviewed suggestions use separate contracts.
  • Writes are staged. Supported attribute values appear in an editable form; the normal platform Save action persists them after review.
  • Evidence stays visible. PDF answers retain page references; tool failures remain distinguishable from answer quality.

Retrieval: two views, two fusion stages

The catalogue path keeps two views of product information. A node collection stores product-level representations; an attribute collection stores smaller attribute or chunk representations linked back to the original node. This gives the search layer different granularities without pretending that every fact belongs in one text blob.

The retrieval configuration uses local Nomic embeddings at 768 dimensions. Qdrant fuses the selected node vectors inside the node branch. A Java-side cross-collection fusion step then combines that branch with the strongest attribute signal per product. The embedding model and index stayed fixed during the fusion experiments, so the ranking changes could be examined separately.

What the reranker changes

A BGE cross-encoder can reorder a fixed candidate pool after fusion. It cannot recover a relevant product that retrieval never supplied. The experiments therefore separated candidate-depth problems from ranking problems.

Evaluation

Evaluation used three separate tracks: 43 semantic ranking cases, 5 exact-identifier cases, and a 25-question full-agent QA run. Keeping them separate prevents a retrieval score from being presented as proof that the complete assistant works.

Development-set results from the signed report. The reranker improved ranking but increased mean CPU latency by roughly 255×, so it stayed optional. Seven per-query regressions were recorded.

The full-agent QA run completed 23 of 25 requests. Mean faithfulness was 0.8338 across the 23 eligible answers. Those numbers are useful because completion and answer quality are reported separately; failed execution does not disappear into an average.

What this evaluation does not prove

It is a development-set evaluation, not a production A/B test. Access was authenticated and read-only. Negative-access security cases were not exhaustively validated, so this is not a security certification. MC15 was migrated and inspected, but it was not benchmarked with the same suite.

Migration to MC15

The MC15 migration changed API contracts and portal lifecycle assumptions. The assistant moved to an explicit model/tool loop, and current-page context became DOM-based. That is real compatibility work, not a version-number bump: page state, tool schemas, and failure handling all have to agree.

I kept the migration separate from the MC14 evidence rather than presenting it as a feature-parity proof. The useful next step is a small regression suite that exercises the critical tool contracts and page-context paths after each platform change.

What I would improve

  • Reranker latency. The quality gain is large, but 26 seconds per request is not an interactive default. Batch scoring, caching, and a faster deployment path need measurement.
  • Security validation. Add explicit absent-principal and negative-access cases to the test suite, then document the boundary rather than inferring it.
  • Evaluation breadth. More questions, inter-annotator agreement, and a blind holdout would make the QA numbers more durable.
  • Observability. Tool-level traces, retrieval candidate counts, and latency percentiles should be first-class evaluation inputs, not afterthoughts.
