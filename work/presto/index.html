The problem

The catalogue contained 107,041 products and the query set contained 29,014 queries. This was a ranking problem, not a classification exercise: for each query, the system had to order a small set of relevant products above a much larger set of plausible ones.

The data made that harder than the model choice suggested. About 90.8% of training positives had no exact catalogue-text match. More than half of the catalogue shared a name with another product: 57,781 of 107,041 entries had duplicate names. A model can learn from queries, but it cannot invent the missing distinction between two similar products.

What I built

I started with a reproducible baseline and added components only when they could be measured. The final system combined complementary candidate sources, fused their rankings, and used a learned reranker on a bounded candidate pool.

  • Query understanding. Normalisation, query expansion, and pseudo-query generation with a small instruction-tuned language model.
  • Dense retrieval. E5 embeddings over product titles and structured text, indexed with HNSW.
  • Lexical retrieval. BM25 and product-name matching to recover exact tokens that embeddings blur.
  • Rank fusion. Weighted reciprocal-rank fusion to combine dense, lexical, and heuristic signals.
  • Reranking. A Jina cross-encoder over the fused candidate pool, with latency measured separately from ranking quality.
  • Fine-tuning. Qwen3-0.6B with LoRA to generate catalogue-style pseudo-queries from product text.

I also prototyped a ColBERT-style late-interaction branch and ran hard-query stratified analysis. Those experiments were useful for diagnosis, but they did not make the final submission.

Evaluation discipline

With eight nights and a public leaderboard, it is easy to overfit to the visible score. I kept a local validation split, recorded each configuration, and separated changes to candidate generation from changes to ranking. I used paired bootstrap intervals on a hard-query subset to check whether small differences were stable enough to keep.

The final leaderboard gain over the organiser baseline was small: 0.62773 versus 0.6241. That is a real result, but not a reason to describe the system as a breakthrough. The top-3 selection cut was 0.69362; I did not reach it.

The result in one sentence

I placed 11th of 50+ with a ranking pipeline that improved on the organiser baseline, but the gap to the top three was larger than another reranker could close.

The diagnosis that mattered

The highest-ROI improvement was not a larger reranker. It was catalogue-text augmentation: generating or enriching product descriptions so that queries and products share meaningful language before retrieval begins. The data showed the gap clearly, but I did not ship that improvement within the challenge window.

That is the honest lesson. The pipeline worked well enough to finish in the top quartile, but the ceiling was set by representation and data, not by the final ranking layer.

Constraints and limits

  • Time. Eight nights, with the final submission taking priority over further research.
  • Compute. A 4 GB RTX 3050 initially, then an A100 40 GB for the heavier runs.
  • Source availability. The original repository and challenge endpoints are offline; the page uses preserved metrics and experiment records, not a reproduced run.
  • Score interpretation. A public leaderboard is not a production search evaluation. The result says the pipeline was competitive, not that it is ready to deploy.

What I would do next

  • Build the catalogue-text augmentation pipeline and measure it against the same validation split.
  • Test a full late-interaction retriever on the hard-query slice, not just a prototype branch.
  • Use a larger query generator with stronger filtering against unsupported product claims.
  • Measure latency and cost per query from the beginning, not only after the ranking pipeline is fixed.
